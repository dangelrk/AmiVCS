Umsetzungsplan v2 · Erweiterung

AMIVCS-GUI

Staging-Bereich, vollständige Multi-Branch-Historie mit echtem Graphen, und eine WebUI — Erweiterung des ersten Entwurfs nach Durchsicht.

Kontext

Drei substanzielle Ergänzungen zum ersten amivcs-gui-Entwurf (Qt+MUI, git-gui-Stil):

  1. Vollständige Historie über mehrere Branches — bisher nur Erster-Elternteil-Kette. Konsole bleibt schlicht (Amiga-Fenster ~70–80 Zeichen breit), aber die GUI bekommt einen echten visuellen Graphen mit Spalten/Linien wie gitk/git log --graph.
  2. Staging-Bereich, dateiweise — kippt die ursprüngliche ADR-09-Entscheidung „kein Staging/Index" bewusst. add/remove von Dateien, Granularität = ganze Datei.
  3. WebUI — nach Login alle Repos des Nutzers mit Historie auflisten, analog zu server/web.php bei AmiCloud.

Diese Version ersetzt den vorherigen Entwurf vollständig. Was dort nicht erwähnt wird, gilt weiterhin unverändert (Bibliotheksaufteilung libs/libcloudvcsgui/, Qt+MUI als Dual-Frontend, Binary-Name amivcs-gui, echtes Abbrechen bei Push/Pull/Clone über ui_hooks.h). Nur Planung — noch nicht implementiert.

1. Staging-Bereich (neu, dateiweise)

Design-Idee: Index = einfach eine Tree-OID

Kein neues Dateiformat nötig — der Staging-Index ist schlicht die OID eines gewöhnlichen VCS_OBJ_TREE-Objekts (existiert schon), gespeichert in einer einzeiligen Datei .amivcs/index. Ein frisches Repo hat einen Index, der exakt HEADs Tree spiegelt.

#define VCS_INDEX_FILE "index"

int vcs_index_load(const char *amivcs_dir, VcsOid *out_tree_oid);
int vcs_index_save(const char *amivcs_dir, const VcsOid *tree_oid);

/* Nach checkout/switch/merge/pull: Index spiegelt wieder den neuen HEAD. */
int vcs_index_reset_to(const char *amivcs_dir, const VcsOid *tree_oid);

/* Hasht/schreibt relpaths aktuellen Inhalt als Blob, schreibt den
 * Index-Tree (+ jeden Eltern-Tree entlang des Pfads) neu. */
int vcs_index_add(VcsRepo *repo, const char *relpath);

/* Entfernt relpath aus dem Index (wie "git rm --cached"). */
int vcs_index_remove(VcsRepo *repo, const char *relpath);

/* "git add -A": staged alle aktuell gemeldeten Aenderungen auf einmal. */
int vcs_index_add_all(VcsRepo *repo);

add/remove nutzen einen „Tree-Pfad neu aufbauen"-Algorithmus: Tree-Objekte entlang des Pfads werden dekodiert, der Blatt-Eintrag ersetzt/entfernt, jede Ebene von unten nach oben neu geschrieben — bis zur neuen Wurzel-OID in .amivcs/index. Nutzt ausschließlich bereits vorhandene Bausteine (vcs_tree_decode/encode/upsert, vcsobjstore_write).

Auswirkung auf repo.h / repo.c

Status wird zweigeteilt (git-Wortlaut):

typedef struct {
    VcsChangeList staged;    /* Index vs. HEAD -- wird committet */
    VcsChangeList unstaged;  /* Arbeitsverzeichnis vs. Index */
} VcsStatus;

int  vcs_repo_status_raw(VcsRepo *repo, VcsStatus *out);
void vcs_status_free(VcsStatus *out);

Commit committet jetzt den Index, nicht mehr das Arbeitsverzeichnis:

int vcs_repo_commit(VcsRepo *repo, const char *author, const char *message,
                    int stage_all, VcsOid *out_oid);

stage_all (CLI: -a/--all) staged vorher automatisch alles. Ohne das Flag muss vorher explizit add aufgerufen worden sein. Commit braucht keinen Arbeitsverzeichnis-Scan mehr — Tree-OID kommt direkt aus dem Index.

vcs_repo_snapshot_workdir() bleibt erhalten (weiter gebraucht von merge.cs konfliktfreiem Merge-Pfad — Merge betrifft potenziell viele Pfade auf einmal, Staging ist dafür kein passendes Modell). vcs_repo_is_dirty() bleibt unverändert.

CLI-Ergänzungen

BefehlWirkung
amivcs add <pfad>...Datei(en) vormerken
amivcs add -AAlle Änderungen vormerken
amivcs remove <pfad>...Aus der Vormerkung entfernen (Datei bleibt erhalten)
amivcs commit -m <text> [-a]Committet Vorgemerktes; -a merkt vorher alles automatisch vor
amivcs statusZeigt „Changes to be committed" + „Changes not staged for commit"
Bestätigt amivcs commit -m ohne vorheriges add committet ab jetzt nichts mehr (git-Konvention) — anders als bisher, wo automatisch der komplette Arbeitsbaum committet wurde. Wer committen will, muss entweder explizit adden (CLI) oder die Dateien in der GUI in den Staging-Bereich verschieben. -a bleibt die Ausnahme-Bequemlichkeit für „alles committen, ohne einzeln zu adden".

2. Vollständige Multi-Branch-Historie + echter Graph

Neue Rohdaten — repo.h / repo.c

typedef struct {
    VcsOid oid;
    VcsOid parents[VCS_MAX_PARENTS];
    int    nparents;
    long   mtime;
    char   author[64];
    char  *message;
    char   decoration[256]; /* Branch-Namen, die genau hier zeigen */
} VcsLogEntry;
typedef struct { VcsLogEntry *items; int n, cap; } VcsLogList;

int vcs_repo_log_raw(VcsRepo *repo, VcsLogList *out);      /* nur 1. Elternteil -- CLI's `log` */
int vcs_repo_log_all_raw(VcsRepo *repo, VcsLogList *out);  /* alle Branches, dedupliziert -- GUI */
void vcs_loglist_free(VcsLogList *list);

Graph-Layout — neu in libs/libcloudvcsgui/

Die Spalten-/Linienzuordnung ist reine Darstellungslogik ohne VCS-Entscheidungscharakter — gehört in die gemeinsame GUI-Bibliothek, wird aber von beiden Frontends genutzt (Qt zeichnet, MUI baut ASCII-Art daraus):

typedef struct {
    int lane;
    int parent_lanes[VCS_MAX_PARENTS];
    int nparent_lanes;
} VcsGraphRow;
typedef struct { VcsGraphRow *items; int n; int max_lanes; } VcsGraphLayout;

int  vcsgui_compute_graph_layout(const VcsLogList *log, VcsGraphLayout *out);
void vcsgui_graph_layout_free(VcsGraphLayout *out);

Standard-Lane-Packing: Commits in Datums-Reihenfolge durchlaufen, „aktive Lanes" führen (jede wartet auf eine Eltern-OID). Trifft ein Commit auf eine wartende Lane, übernimmt er ihre Spalte; bei einem zweiten Elternteil (Merge) wird eine zusätzliche Lane eingefügt. Freiwerdende Lanes werden wiederverwendet, damit der Graph nicht unbegrenzt breit wird.

* ┃ bae63ed Merge branch 'feature' ┃╲ ┃ * ca6e258 feature: add d.txt * ┃ 9149eb6 main: add c.txt ┃╱ * 88e1faa first commit

Qt zeichnet dies als QPainter-Grafik in einer eigenen Delegate-Spalte. MUI braucht kein Custom-BOOPSI-Zeichnen — dieselbe VcsGraphLayout wird zu genau dieser Art ASCII-Spalte zusammengesetzt und einfach im bestehenden MUIA_List_DisplayHook ausgegeben. Passt exakt zur schmalen Amiga-Fensterbreite und zur „nur eingebaute Klassen"-Konvention des Commanders.

3. Auswirkung auf den GUI-Funktionsumfang

Die „Änderungsliste" aus dem ersten Entwurf wird zweigeteilt Ersetzt v1:

  • Nicht vorgemerkte Änderungen — Vormerken-Button/Doppelklick verschiebt Dateien in den Staging-Bereich.
  • Vorgemerkte Änderungen — Entfernen-Button verschiebt zurück; „Alles vormerken"-Knopf.
  • Commit committet nur, was vorgemerkt ist.
  • Historie zeigt jetzt den vollen Multi-Branch-Graphen, nicht mehr nur die Kette.

    ...

4. Neu: AMIVCS-WebUI

Analog zu server/web.php bei AmiCloud — eigene Session/Login, eigene Tabellen, kein gemeinsamer Code mit dem Cloud-Server.

Login — exakt das verifizierte Muster von server/web.php

session_set_cookie_params(['lifetime'=>0,'path'=>'/','secure'=>true,'httponly'=>true,'samesite'=>'Strict']);
session_start();
// CSRF-Token in $_SESSION, per hash_equals() bei POST geprueft
// password_verify() gegen amivcs.users.pass_hash
// session_regenerate_id(true) nach Login, session_destroy() bei Logout

Getrennt von api.phps zustandslosem HTTP-Basic-Auth (für C-Clients) — eigene formularbasierte Session für Menschen im Browser.

Seiten (v1-Umfang)

SeiteInhalt
Repo-Liste (nach Login)Alle eigenen Repos, Branch-Anzahl, letzter Commit
Repo-DetailBranch-Liste + volle Multi-Branch-Historie als HTML/CSS-Tabelle mit Lane-Indikatoren (kein interaktiver JS-Graph, serverseitig vorgerechnet)

Bewusst nicht in v1: kein Datei-/Baum-Browser, kein Diff-View, kein Commit/Push/Pull aus dem Browser, keine Repo-Anlage über die WebUI — ein Repo-Überblick mit Historie, kein GitHub-Nachbau.

Neue serverseitige Bausteine

  • includes/ObjectDecoder.php — liest Tree-/Commit-Objekte aus dem Storage, dekodiert das binäre Format (Varint-Lesen, Tree-/Commit-Layout aus object.c in PHP nachgebildet) — rein lesend, nur für Anzeige.
  • includes/GraphLayout.php — PHP-Portierung des Lane-Algorithmus aus §2.
Architektur-Hinweis ADR 09 legt fest, dass der Server keinerlei VCS-Logik besitzt (Merge-/Ancestry-Entscheidungen). Objekte für eine reine Nur-Lese-Anzeige zu dekodieren ist etwas anderes (Darstellung, keine Entscheidung) — aber neuer Code, den die ursprüngliche ADR nicht vorgesehen hat. Bewusst als schmale, ausdrücklich gewünschte Ausnahme markiert.

5. Geplante Implementierungsreihenfolge ersetzt v1

  1. Staging-Modul (index.h/index.c) + zweigeteilter Status + Commit-Umbau + CLI add/remove/-a. libcloudvcs: file-level staging area (add/remove/index)
  2. Volle Multi-Branch-Historie (vcs_repo_log_all_raw + Decorations). libcloudvcs: full multi-branch history with decorations
  3. Graph-Layout-Algorithmus in libcloudvcsgui — reine Datenberechnung, host-testbar. libcloudvcsgui: commit graph lane layout
  4. libcloudvcsgui-Session-Kern + Cancel/Progress-Anbindung (wie im ersten Entwurf). libcloudvcsgui: headless GUI session/controller
  5. Qt-Frontend — inkl. Staged/Unstaged-Ansicht + gezeichnetem Graphen. amivcs-gui-qt: Qt6 git-gui-style frontend
  6. MUI-Frontend — inkl. Staged/Unstaged-Ansicht + ASCII-Graph-Spalte. amivcs-gui-mui: MUI 3.8 frontend
  7. AMIVCS-WebUI (web.php + ObjectDecoder.php + GraphLayout.php). amivcs-server: web UI (repo list + history)
  8. Doku — GUI- und WebUI-Kapitel ergänzen. docs: AMIVCS GUI + WebUI chapters

6. Verifikation

Stufe 1: frisches Repo → status leer; Datei anlegen → „not staged"; add → „to be committed"; commit -m ohne -a committet nur Vorgemerktes; zweite Datei anlegen, nicht adden, commit -m → bleibt unstaged, kein Fehler; commit -a staged+committet den Rest. Nach switch/checkout ist der Index sauber.

Stufe 2: Repo mit zwei divergierenden Branches + einem Merge — log_all_raw() muss beide Linien plus Merge-Commit zeigen, jeder Commit genau einmal, korrekte Decorations.

Stufe 3: gleiches Test-Repo — Lane-Zuordnung von Hand nachvollziehen.

Stufen 5–6: wie im ersten Entwurf, ergänzt um Datei vormerken/zurücknehmen, Teil-Commit, Graph-Ansicht mit echtem Merge-Szenario.

Stufe 7: Login-Session + CSRF-Schutz testen, Repo-Liste zeigt nur eigene Repos, Historie-Ansicht stimmt mit der GUI-Ansicht überein.

Regressions-Sicherung: bestehende CLI-Tests (init/branch/switch/checkout/merge/gc/ clone/push/pull) funktionieren unverändert, abgesehen von der bewusst geänderten commit-Semantik.
